Run on Kubernetes

The same stack as docker compose (see the how-to), packaged for Kubernetes with Kustomize in deploy/k8s/: one base plus a local overlay (kind, k3d, minikube, Docker Desktop) and a cloud overlay (EKS, GKE, AKS…). You do not need Kubernetes to use the data. The map, downloads and MCP server work without it. Kubernetes is for running your own always-on copy with a live database and APIs.

Folder layout

What

A Kustomize base with every resource, and two small overlays that patch it.

Why

Kustomize ships inside kubectl (kubectl apply -k), so there is no extra tool and no templating language. Overlays keep local and cloud differences (image names, storage size, replicas, Ingress) to a few lines.

Alternatives

  • Helm chart: better for publishing to many users with lots of knobs, but more templating than five workloads need.
  • Plain YAML: works, but you would copy-edit files for each environment.

The code

deploy/k8s/
├── base/
│   ├── kustomization.yaml       # namespace, labels, configMapGenerator for initdb SQL
│   ├── namespace.yaml
│   ├── secret.example.yaml      # placeholders only
│   ├── postgis.yaml             # StatefulSet + headless Service
│   ├── harvester-cronjob.yaml
│   ├── featureserv.yaml         # Deployment + Service
│   ├── martin.yaml              # Deployment + Service
│   ├── mcp.yaml                 # Deployment + Service (streamable HTTP)
│   └── initdb/01_init.sql       # copy of sql/01_init.sql
└── overlays/
    ├── local/                   # local images, 3 Gi PVC, CronJob suspended; harvest-one.yaml Job
    └── cloud/                   # 2 replicas per API, 20 Gi PVC + storageClass, Ingress

Gotchas

  • Kustomize refuses files outside the kustomization folder, so sql/01_init.sql is copied into base/initdb/. Keep the two copies in sync.

Namespace

What

Everything lives in namespace sjrwmd. The base sets it once with namespace:.

Why

One namespace keeps teardown to a single kubectl delete ns sjrwmd and makes quotas and RBAC simple.

The code

apiVersion: v1
kind: Namespace
metadata:
  name: sjrwmd

Secret (placeholders only)

What

One Secret sjrwmd-db holds the superuser password, the loader password, and the reader connection URL that the three APIs use.

Why

The services read credentials from secretKeyRef, so no password is baked into an image or a Deployment. The file in git uses the same change_me_* placeholders as docker compose.

Alternatives

  • Sealed Secrets (encrypted YAML safe to commit)
  • External Secrets Operator pulling from AWS Secrets Manager, GCP Secret Manager or Azure Key Vault
  • CloudNativePG generates the app user secret for you (see below)

The code

# PLACEHOLDERS ONLY. Replace before any real deployment, e.g.
#   kubectl -n sjrwmd create secret generic sjrwmd-db --from-literal=... --dry-run=client -o yaml | kubeseal ...
# or use External Secrets / your cloud secret manager. Never commit real values.
# The role passwords must match those set by initdb/01_init.sql (change them there too, or ALTER ROLE after init).
apiVersion: v1
kind: Secret
metadata:
  name: sjrwmd-db
type: Opaque
stringData:
  POSTGRES_PASSWORD: change_me_postgres
  LOADER_PASSWORD: change_me_loader
  READER_URL: postgres://sjrwmd_reader:change_me_reader@postgis:5432/sjrwmd

Gotchas

  • The role passwords are created by 01_init.sql on first start only. If you change the Secret later, also run ALTER ROLE … PASSWORD.
  • Base64 in a Secret is encoding, not encryption. Enable etcd encryption or use one of the alternatives in production.

PostGIS as a StatefulSet

What

postgis/postgis:17-3.5 in a 1-replica StatefulSet with a volumeClaimTemplate (10 Gi in the base) and a headless Service postgis. The init SQL is mounted from a ConfigMap into /docker-entrypoint-initdb.d.

Why

A StatefulSet gives the pod a stable name and its own PersistentVolumeClaim that survives restarts and rescheduling. The 15 layers use about 1.2 GB with indexes (land use alone is 447 MB), so 10 Gi leaves room for growth or --all.

Alternatives

  • CloudNativePG: an operator that runs Postgres with streaming replicas, automatic failover, and backups/PITR to S3, GCS or Azure. Use the ghcr.io/cloudnative-pg/postgis image and add postgis in bootstrap.initdb.postInitApplicationSQL. This is the recommended choice for anything beyond a demo.
  • Managed Postgres (RDS, Cloud SQL, Azure Flexible Server; all support PostGIS): delete postgis.yaml and point the Secret URLs at it.

The code

# Single-instance PostGIS. For HA, backups and failover use the CloudNativePG operator instead
# (Cluster resource with imageName ghcr.io/cloudnative-pg/postgis:17) -- see the "Run on Kubernetes" tab.
apiVersion: v1
kind: Service
metadata:
  name: postgis
spec:
  clusterIP: None
  selector: {app: postgis}
  ports: [{name: pg, port: 5432}]
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgis
spec:
  serviceName: postgis
  replicas: 1
  selector: {matchLabels: {app: postgis}}
  template:
    metadata: {labels: {app: postgis}}
    spec:
      securityContext: {fsGroup: 999}
      containers:
        - name: postgis
          image: postgis/postgis:17-3.5
          ports: [{name: pg, containerPort: 5432}]
          env:
            - {name: POSTGRES_DB, value: sjrwmd}
            - {name: POSTGRES_USER, value: postgres}
            - name: POSTGRES_PASSWORD
              valueFrom: {secretKeyRef: {name: sjrwmd-db, key: POSTGRES_PASSWORD}}
            - {name: PGDATA, value: /var/lib/postgresql/data/pgdata}
          volumeMounts:
            - {name: data, mountPath: /var/lib/postgresql/data}
            - {name: initdb, mountPath: /docker-entrypoint-initdb.d, readOnly: true}
          resources:
            requests: {cpu: 250m, memory: 512Mi}
            limits: {cpu: "2", memory: 2Gi}
          readinessProbe:
            exec: {command: [pg_isready, -U, postgres, -d, sjrwmd]}
            periodSeconds: 10
          livenessProbe:
            exec: {command: [pg_isready, -U, postgres, -d, sjrwmd]}
            initialDelaySeconds: 30
            periodSeconds: 20
      volumes:
        - name: initdb
          configMap: {name: postgis-initdb}
  volumeClaimTemplates:
    - metadata: {name: data}
      spec:
        accessModes: [ReadWriteOnce]
        resources: {requests: {storage: 10Gi}}   # 15 layers ~1.2 GB incl. indexes; headroom for --all

Gotchas

  • PGDATA is set to a subfolder because many volumes have a lost+found directory at the root, which makes initdb fail.
  • Deleting the StatefulSet does not delete the PVC. That is deliberate. Delete the namespace or PVC to really wipe data.

Harvester as a weekly CronJob

What

Runs python harvest.py from the repo Dockerfile every Monday 06:00 (cluster time, usually UTC), as the sjrwmd_loader role.

Why

The harvester is incremental: a layer whose lastEditDate, count and schema have not changed is skipped in about 1 s, so a weekly run is cheap. The full first load of all 15 layers was about 883 s of layer time (land use alone was 455 s). concurrencyPolicy: Forbid stops two runs from overlapping, and activeDeadlineSeconds: 7200 kills a stuck run.

The code

# Weekly harvest. Unchanged layers are skipped (~1 s each); a full first load of the 15 layers took ~883 s of layer time.
# Run once by hand:  kubectl -n sjrwmd create job harvest-now --from=cronjob/harvester
apiVersion: batch/v1
kind: CronJob
metadata:
  name: harvester
spec:
  schedule: "0 6 * * 1"          # Mondays 06:00 (cluster time zone, usually UTC)
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 2
  failedJobsHistoryLimit: 3
  jobTemplate:
    spec:
      backoffLimit: 2
      activeDeadlineSeconds: 7200
      template:
        spec:
          restartPolicy: Never
          containers:
            - name: harvest
              image: ghcr.io/knightchrism/sjrwmd-harvest:latest   # build from the repo Dockerfile
              args: []                                             # e.g. ["--only", "management_area"]
              env:
                - {name: PGHOST, value: postgis}
                - {name: PGDATABASE, value: sjrwmd}
                - {name: PGUSER, value: sjrwmd_loader}
                - name: PGPASSWORD
                  valueFrom: {secretKeyRef: {name: sjrwmd-db, key: LOADER_PASSWORD}}
              resources:
                requests: {cpu: 250m, memory: 512Mi}
                limits: {cpu: "1", memory: 2Gi}
# Dockerfile (repo root)
# Harvester image: python harvest.py [--only ALIAS ...]
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY harvest.py layers.yaml esri_inventory.csv ./
USER 10001
ENTRYPOINT ["python", "harvest.py"]

Gotchas

  • The image is not published to a registry. Build it yourself (step-by-step below). The local overlay renames it to sjrwmd-harvest:dev.
  • The local overlay sets suspend: true so a laptop cluster does not start a full harvest on its own. Trigger runs by hand with kubectl create job --from=cronjob/harvester.
  • The pod needs egress to services.arcgis.com. Strict NetworkPolicies must allow it.

pg_featureserv

What

A Deployment and Service on port 9000 serving OGC API – Features (GeoJSON) from the sjrwmd views, connected as the read-only role.

Why

It is stateless, so it scales horizontally and restarts freely. The readiness probe hits /collections.json, which needs a working DB connection, so traffic only goes to pods that can actually answer.

The code

apiVersion: apps/v1
kind: Deployment
metadata:
  name: featureserv
spec:
  replicas: 1
  selector: {matchLabels: {app: featureserv}}
  template:
    metadata: {labels: {app: featureserv}}
    spec:
      containers:
        - name: featureserv
          image: pramsey/pg_featureserv:latest
          ports: [{name: http, containerPort: 9000}]
          env:
            - name: DATABASE_URL
              valueFrom: {secretKeyRef: {name: sjrwmd-db, key: READER_URL}}
          resources:
            requests: {cpu: 50m, memory: 64Mi}
            limits: {cpu: 500m, memory: 256Mi}
          readinessProbe:
            httpGet: {path: /collections.json, port: http}
            periodSeconds: 10
          livenessProbe:
            httpGet: {path: /, port: http}
            initialDelaySeconds: 15
            periodSeconds: 30
---
apiVersion: v1
kind: Service
metadata:
  name: featureserv
spec:
  selector: {app: featureserv}
  ports: [{name: http, port: 9000, targetPort: http}]

Martin vector tiles

What

A Deployment and Service on port 3000 serving MVT tiles straight from PostGIS, auto-discovering the tables and views.

Why

The static site uses prebuilt PMTiles; Martin is for a live copy where tiles reflect the latest harvest without re-running tippecanoe. Probes use Martin's built-in /health.

The code

kind: Deployment
metadata:
  name: martin
spec:

  selector: {matchLabels: {app: martin}}

            limits: {cpu: "1", memory: 512Mi}
          readinessProbe:
            httpGet: {path: /health, port: http}
            periodSeconds: 10
          livenessProbe:
            httpGet: {path: /health, port: http}
            initialDelaySeconds: 10
            periodSeconds: 30
---
apiVersion: v1
kind: Service
metadata:
  name: martin
spec:
  selector: {app: martin}
  ports: [{name: http, port: 3000, targetPort: http}]

Gotchas

  • Put a CDN or caching proxy in front of Martin in the cloud. Tiles are very cacheable, and the busiest layers (land use, ERP) are the most expensive to render on the fly.

MCP server over streamable HTTP

What

sjrwmd-mcp runs as a Deployment on :8000/mcp using the MCP SDK's streamable HTTP transport (set SJRWMD_MCP_TRANSPORT=streamable-http). With DATABASE_URL set it queries PostGIS read-only; remove it to fall back to DuckDB on the published GeoParquet.

Why

Over stdio, each AI client starts its own server process. Over HTTP, one shared server in the cluster can serve a whole team, and clients only need a URL. The same safety rules apply in both modes: whitelisted layers and fields, parameterized SQL, max 500 rows, a read-only transaction and a 30 s statement timeout.

The code

# MCP server over streamable HTTP at http://mcp:8000/mcp. Uses PostGIS (read-only role) via DATABASE_URL.
# Remove DATABASE_URL to use the DuckDB backend on the published GeoParquet instead (needs egress to github.com).
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mcp
spec:
  replicas: 1
  selector: {matchLabels: {app: mcp}}
  template:
    metadata: {labels: {app: mcp}}
    spec:
      securityContext: {runAsNonRoot: true, runAsUser: 10001}
      containers:
        - name: mcp
          image: ghcr.io/knightchrism/sjrwmd-mcp:latest   # build from mcp/Dockerfile
          ports: [{name: http, containerPort: 8000}]
          env:
            - {name: SJRWMD_MCP_TRANSPORT, value: streamable-http}
            - {name: SJRWMD_MCP_HOST, value: 0.0.0.0}
            - {name: SJRWMD_MCP_PORT, value: "8000"}
            - name: DATABASE_URL
              valueFrom: {secretKeyRef: {name: sjrwmd-db, key: READER_URL}}
          resources:
            requests: {cpu: 50m, memory: 128Mi}
            limits: {cpu: "1", memory: 1Gi}
          readinessProbe:
            tcpSocket: {port: http}
            periodSeconds: 10
          livenessProbe:
            tcpSocket: {port: http}
            initialDelaySeconds: 10
            periodSeconds: 30
---
apiVersion: v1
kind: Service
metadata:
  name: mcp
spec:
  selector: {app: mcp}
  ports: [{name: http, port: 8000, targetPort: http}]
# MCP server image (streamable HTTP on :8000/mcp). Build: docker build -t sjrwmd-mcp:dev mcp/
FROM python:3.12-slim
WORKDIR /app
COPY . .
RUN pip install --no-cache-dir ".[postgis]"
USER 10001
ENV SJRWMD_MCP_TRANSPORT=streamable-http SJRWMD_MCP_HOST=0.0.0.0 SJRWMD_MCP_PORT=8000 HOME=/tmp
EXPOSE 8000
ENTRYPOINT ["sjrwmd-mcp"]
// VS Code .vscode/mcp.json pointing at the cluster
{"servers": {"sjrwmd": {"type": "http", "url": "https://mcp.example.org/mcp"}}}

Gotchas

  • The HTTP endpoint has no authentication built in. Keep it cluster-internal, or put it behind your Ingress auth (OAuth2 proxy, basic auth, IP allowlist) before exposing it.
  • The SDK's DNS-rebinding guard rejects non-localhost Host headers, so the server turns it off when bound to 0.0.0.0. Rely on the Ingress host rules instead.
  • Streamable HTTP keeps sessions in memory. With 2+ replicas, enable sticky sessions on the Ingress or keep 1 replica.

Ingress example

What

The cloud overlay adds an ingress-nginx Ingress with cert-manager TLS and one host per service: features., tiles. and mcp..

Why

Separate hosts avoid path rewriting. pg_featureserv and Martin generate absolute links and expect to be served at /. Rate limiting and a longer read timeout (for streamed MCP responses) are set as annotations.

Alternatives

  • Gateway API HTTPRoute
  • Cloud load balancer Services (type: LoadBalancer), one per service, which cost more

The code

# Example only: ingress-nginx + cert-manager. One host per service so no path rewriting is needed.
# Replace example.org with your domain.
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: sjrwmd
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt
    nginx.ingress.kubernetes.io/proxy-read-timeout: "300"   # MCP streams responses
    nginx.ingress.kubernetes.io/limit-rps: "10"
spec:
  ingressClassName: nginx
  tls: [{hosts: [features.example.org, tiles.example.org, mcp.example.org], secretName: sjrwmd-tls}]
  rules:
    - host: features.example.org
      http: {paths: [{path: /, pathType: Prefix, backend: {service: {name: featureserv, port: {name: http}}}}]}
    - host: tiles.example.org
      http: {paths: [{path: /, pathType: Prefix, backend: {service: {name: martin, port: {name: http}}}}]}
    - host: mcp.example.org
      http: {paths: [{path: /mcp, pathType: Prefix, backend: {service: {name: mcp, port: {name: http}}}}]}

Requests, limits and probes

What

Every container has CPU/memory requests and limits plus readiness and liveness probes.

Why

Requests let the scheduler place pods correctly, and limits stop a runaway query from starving the node. Readiness keeps traffic off pods that are not ready; liveness restarts hung ones.

The code

WorkloadRequestsLimitsReadiness / liveness
postgis250m / 512Mi2 / 2Gipg_isready
harvester250m / 512Mi1 / 2Gi(Job: deadline + backoffLimit 2)
featureserv50m / 64Mi500m / 256MiHTTP /collections.json, /
martin100m / 128Mi1 / 512MiHTTP /health
mcp50m / 128Mi1 / 1GiTCP :8000

These are starting points, not measurements from a cluster. Tune them from kubectl top pods.

Gotchas

  • The harvester's memory peaks while it assembles land-use polygons. If it is OOMKilled, raise its limit rather than the page size.

Step by step

What

Build the images, create a local cluster, apply the stack, load one small layer, and check the APIs.

Why

This is the shortest path from zero to a working cluster. Each command is plain kubectl/kind.

The code

# 0. tools: docker (or podman), kind (or k3d), kubectl
git clone https://github.com/knightchrism/sjrwmd-open-data && cd sjrwmd-open-data

# 1. build images and a throwaway cluster
docker build -t sjrwmd-harvest:dev .
docker build -t sjrwmd-mcp:dev mcp/
kind create cluster --name sjrwmd
kind load docker-image sjrwmd-harvest:dev sjrwmd-mcp:dev --name sjrwmd   # k3d: k3d image import ...

# 2. preview, then apply
kubectl kustomize deploy/k8s/overlays/local | less
kubectl apply -k deploy/k8s/overlays/local
kubectl -n sjrwmd rollout status statefulset/postgis
kubectl -n sjrwmd get pods

# 3. harvest one small layer (management_area: 133 features)
kubectl -n sjrwmd apply -f deploy/k8s/overlays/local/harvest-one.yaml
kubectl -n sjrwmd wait --for=condition=complete job/harvest-one --timeout=10m
kubectl -n sjrwmd logs job/harvest-one
kubectl -n sjrwmd rollout restart deploy/featureserv deploy/martin   # pick up the new table

# 4. check the APIs
kubectl -n sjrwmd port-forward svc/featureserv 9000:9000 &
kubectl -n sjrwmd port-forward svc/martin 3000:3000 &
kubectl -n sjrwmd port-forward svc/mcp 8000:8000 &
curl -s localhost:9000/collections.json | jq '.collections[].id'
curl -s "localhost:9000/collections/sjrwmd.management_area/items.json?limit=1" | jq '.features[0].properties'
curl -s localhost:3000/catalog | jq 'keys'

# 5. tear down
kind delete cluster --name sjrwmd

# cloud: push images to your registry, edit the images/hosts, then
kubectl apply -k deploy/k8s/overlays/cloud

Gotchas

  • On Apple Silicon or ARM nodes, build multi-arch images (docker buildx build --platform linux/amd64,linux/arm64).
  • pg_featureserv and Martin only see tables that exist when they start. Restart them after the first harvest: kubectl -n sjrwmd rollout restart deploy/featureserv deploy/martin.

Scaling notes

What

How each piece grows.

Why

Most traffic here is reads, so scale the stateless readers first and the database last.

The code

  • featureserv, martin, mcp: stateless; raise replicas or add a HorizontalPodAutoscaler on CPU. Each holds a small connection pool, so watch total connections against Postgres max_connections (default 100); add PgBouncer if you go past ~10 pods.
  • Tiles: a CDN in front of Martin helps far more than extra replicas.
  • PostGIS: scale up (CPU/RAM) first. For read replicas and failover, move to CloudNativePG with instances: 3 and point readers at its -ro Service.
  • Harvester: one Job at a time. workers: 2 in layers.yaml is deliberately polite to SJRWMD's servers; do not raise it just because the cluster can.
  • Static site: GitHub Pages and the PMTiles need no cluster at all and scale for free.

What

Rough monthly costs. These are estimates based on typical 2026 list prices, not quotes or measured bills. Check your provider's calculator.

Why

For read-mostly public data the cheapest option is often no cluster at all.

What was actually tested

On Oct 28, 2026, on the build machine (no Docker or other container runtime was available there, so no live cluster was created):

  • kubectl kustomize (kubectl v1.37.2) rendered both overlays: 12 resources (local) and 13 (cloud).
  • kubeconform v0.8.0 -strict validated every rendered resource against the Kubernetes schemas: 12/12 and 13/13 valid, 0 errors.
  • The MCP server's streamable-HTTP mode was run for real (SJRWMD_MCP_TRANSPORT=streamable-http): an MCP client listed 7 tools and ran find_near over http://…/mcp.
  • The harvester command the one-off Job runs (harvest.py --only management_area) was run against a local PostGIS (no container): 133 of 133 features fetched, matching the server, in 3.3 s.
  • harvest-one.yaml also passes kubeconform.

Not yet tested: applying to a running cluster, image builds, the harvester Job, and port-forward curls. The step-by-step commands above are what to run on a machine with Docker and kind.
