1. Picking the source: ArcGIS REST, not Hub downloads

What we do

Read every layer straight from SJRWMD's ArcGIS Online REST services: https://services.arcgis.com/s8wtJX9suxFen6TA/ArcGIS/rest/services (230 FeatureServers, 454 layers, 7,158,579 features in our inventory). The Hub, data-floridaswater.opendata.arcgis.com, is used only for metadata: 175 datasets, matched to 342 layers, and their item ids go into _hub_item_id.

Why

The REST API is the system of record behind the Hub. It exposes field types, editingInfo.lastEditDate, server-side reprojection (outSR), exact counts and OBJECTID queries: everything needed for typed tables, incremental updates and count checks. Hub downloads are generated files whose freshness and schema we can't control.

Alternatives considered

  • Hub downloads (CSV, shapefile, GeoJSON, file geodatabase): one click for a person, but cached exports can lag the live layer, shapefiles truncate field names to 10 characters and dates to day precision, and there is no per-layer change signal to drive incremental updates.
  • Scraping the web viewers: fragile and pointless when the same data is offered as an API.
  • Asking SJRWMD for a database dump: not reproducible by anyone else, and not needed for public data.

The code in this repo

BASE=https://services.arcgis.com/s8wtJX9suxFen6TA/ArcGIS/rest/services
L=$BASE/SJRWMD_Management_Area_viewLayer/FeatureServer/0
curl -s "$L?f=json" | jq '{name, geometryType, maxRecordCount, objectIdField, lastEdit: .editingInfo.lastEditDate}'
curl -s "$L/query?where=1%3D1&returnCountOnly=true&f=json"      # {"count":133}

Gotchas we hit

  • Several services are "view layers" (e.g. SJRWMD_Management_Area_viewLayer) rather than the underlying hosted layer; they are what's public, so we read those.
  • Hub dataset ids don't map 1:1 to layers (175 datasets cover 342 of 454 layers), so _hub_item_id is null for some rows.

2. Discovering layers and fields

What we do

scripts/enumerate_esri.py walks the services directory, reads every layer's JSON, and writes esri_inventory.csv (service, layer id, geometry type, feature count, maxRecordCount, change tracking, last edit, hub item id). layers.yaml then selects 15 of them with a one-line reason each and a short alias.

Why

A machine-generated inventory makes the selection reviewable and repeatable, and gives each layer's field list and paging limit up front. The 15 were chosen for usefulness and clean API use: 5 polygon, 5 point, 5 line, with stable ids, typed dates and status fields, and joinable permit numbers.

Alternatives considered

  • Mirroring all 454 layers: we started that and stopped. Many are derived products or near-duplicates, and the long tail adds hours without adding value for the map or the downloads.
  • Hand-picking from the Hub UI: no record of field types or limits, hard to repeat.

The code in this repo

Gotchas we hit

  • Service names are inconsistent (Consumption_Use_Permit__CUP vs Consumptive_Use_Permit_CUP_Boundary), hence friendly aliases.
  • One service can hold several useful layers (status_trend_2025_all_stations layers 0 and 2), so the key is service/layer_id.

3. Paging, maxRecordCount, throttling and retries

What we do

Ask for all OBJECTIDs once (returnIdsOnly=true), sort them, then request fixed chunks by OBJECTID range with page size = min(1000, the layer's maxRecordCount). Two layers are fetched in parallel, with a 0.3 s pause before every request and up to 6 attempts with exponential backoff on HTTP 429/5xx or an Esri error body.

Why

Every layer caps a response at maxRecordCount (2,000 on 403 layers, 1,000 on 51 in our inventory). OBJECTID ranges are deterministic: each chunk is independent, a retried chunk returns the same rows, and nothing is skipped or duplicated if the server's default ordering shifts. Two workers and a delay keep us a polite guest on a public service.

Alternatives considered

  • resultOffset paging (what GDAL's ESRIJSON driver and many scripts use): fine for small layers, but offsets on an unsorted query can skip or repeat rows, and it isn't supported on every layer.
  • One giant request: silently truncated at maxRecordCount (the response just sets exceededTransferLimit).
  • More parallelism: faster, but a public agency server is not ours to load-test.

The code in this repo

def get(url, **params):
    params.setdefault("f", "json")
    for attempt in range(6):
        time.sleep(DELAY)                                   # 0.3 s between requests
        try:
            r = session().post(url, data=params, timeout=180)
            if r.status_code in (429, 500, 502, 503, 504):
                raise requests.HTTPError(f"HTTP {r.status_code}")
            r.raise_for_status(); d = r.json()
            if isinstance(d, dict) and "error" in d: raise RuntimeError(json.dumps(d["error"])[:300])
            return d
        except Exception:
            if attempt == 5: raise
            time.sleep(min(60, 2 ** attempt * 2))           # 2, 4, 8, 16, 32 s

ids = sorted(get(f"{url}/query", where="1=1", returnIdsOnly="true").get("objectIds") or [])
page = min(cfg.get("page_size", 1000), info.get("maxRecordCount") or 1000)
for i in range(0, len(ids), page):
    chunk = ids[i:i + page]
    d = get(f"{url}/query", where=f"{oid_field} >= {chunk[0]} AND {oid_field} <= {chunk[-1]}",
            outFields="*", outSR=srid, returnGeometry="true")

Gotchas we hit

  • ArcGIS returns errors as HTTP 200 with an {"error": …} body, so status codes alone aren't enough; we check the body too.
  • We use POST, because long where clauses and parameters can exceed URL length limits.
  • Real timings (seconds per layer): land use 2020 454.9 s for 309,325 polygons; ERP 132.1 s; streams 84.1 s; CUP stations 67.6 s; management areas 3.2 s.

4. Output format: Esri JSON, not GeoJSON

What we do

Request f=json (Esri JSON) and build geometries ourselves with Shapely: polygon rings are grouped by orientation, clockwise = outer ring, counter-clockwise = hole, and each hole is attached to the smallest outer ring that contains it.

Why

The server's f=geojson output emitted every ring as its own polygon, so holes came back as separate "nested shell" polygons stacked on their parents. Esri JSON keeps the rings and their orientation, which is all we need to rebuild correct polygons, the same way GDAL does.

Alternatives considered

  • f=geojson: convenient, but wrong for polygons with holes on this server.
  • f=pbf (protocol buffers): smaller, but not supported uniformly and harder to debug.
  • ogr2ogr on the REST URL: correct ring handling and great for one-off loads (see step 15), but we wanted typed columns, provenance and hash-diff upserts in one pass.

The code in this repo

if gtype == "esriGeometryPolygon":
    shells, holes = [], []
    for ring in g.get("rings", []):
        pts = [tuple(p[:2]) for p in ring]
        if len(pts) < 4: continue
        lr = LinearRing(pts)
        (holes if lr.is_ccw else shells).append(lr)   # Esri: clockwise = exterior
    if not shells:                                     # some services return all rings counter-clockwise
        shells, holes = holes, []
    polys = [[s, []] for s in shells]; sp = [Polygon(s) for s in shells]
    for h in holes:                                    # attach each hole to the smallest shell covering it
        pt = Point(h.coords[0]); best = None
        for i, p in enumerate(sp):
            if p.covers(pt) and (best is None or p.area < sp[best].area): best = i
        if best is None: polys.append([LinearRing(list(h.coords)[::-1]), []])
        else: polys[best][1].append(h)
    return MultiPolygon([Polygon(s, hs) for s, hs in polys])

Gotchas we hit

  • On District Management Areas, switching from GeoJSON to ring assembly cut invalid geometries from 30 to 10. The remaining 10 are rings that touch themselves, which Esri allows and OGC doesn't; the harvester repairs those with ST_MakeValid and flags them in _geom_repaired.
  • Some layers return all rings counter-clockwise; with no clockwise ring we treat them all as shells rather than producing empty polygons.

5. Reprojection: EPSG:3086 tables, EPSG:4326 views

What we do

Ask the server to reproject (outSR=3086) and store geom in EPSG:3086, NAD83 / Florida GDL Albers (meters). Every table also gets a <table>_4326 view that transforms to WGS84 on the fly for web maps, tiles and GeoParquet.

Why

Florida GDL Albers is an equal-area projection that covers the whole state, so ST_Area, ST_Length and ST_DWithin give real meters and acres with plain, index-friendly geometry math. Web tools (MapLibre, tippecanoe, GeoJSON, GeoParquet consumers) expect longitude/latitude, hence the 4326 view. One stored copy, two coordinate systems, no drift.

Alternatives considered

  • Store 4326 only: distances and areas then need geography casts or spheroid functions, which are slower and easy to get wrong.
  • Florida State Plane (East/North zones, feet): SJRWMD spans two zones; one statewide meter-based CRS is simpler.
  • Store both columns: doubles storage and invites them to get out of sync.

The code in this repo

CREATE OR REPLACE VIEW sjrwmd.sjrwmd_management_area_viewlayer_0_4326 AS
SELECT t.source_oid, t.objectid, t.county, t.conservation_area, t.acres, ...,   -- every column except geom
       ST_Transform(t.geom, 4326)::geometry(MultiPolygon, 4326) AS geom
FROM sjrwmd.sjrwmd_management_area_viewlayer_0 t;

Gotchas we hit

  • The view must cast to a typed geometry(MultiPolygon, 4326); otherwise GDAL and Martin can't detect the geometry type and SRID.
  • PROJ printed harmless grid warnings (us_noaa_alhpgn.tif) on transform; set PROJ_NETWORK=ON or install proj-data to silence them.

6. Typed columns from Esri field types

What we do

Build each table's columns from the layer's fields list, mapping esriFieldType to a PostgreSQL type, and normalize values on the way in (Esri dates arrive as epoch milliseconds).

esriFieldTypePostgreSQL
OIDbigint
SmallInteger / Integer / BigIntegersmallint / integer / bigint
Single / Doublereal / double precision
String, GUID, GlobalID, XMLtext
Date, TimestampOffsettimestamptz (from epoch ms)
DateOnlydate
TimeOnlytime
Geometry / Blob / Rasterskipped (geometry goes to geom)

Why

Typed columns make WHERE prmt_decision_dt >= '2020-01-01', numeric sorting and sums work correctly, and they carry through to the GeoPackage and GeoParquet exports.

Alternatives considered

  • One jsonb attributes column: flexible, but every query needs casts, and exports and tile attributes lose their types. It is still available with keep_raw_attrs: true.
  • Everything as text: what CSV-based loaders produce; dates sort as strings and numbers as text.

The code in this repo

TYPES = {"esriFieldTypeSmallInteger": "smallint", "esriFieldTypeInteger": "integer", "esriFieldTypeBigInteger": "bigint",
         "esriFieldTypeSingle": "real", "esriFieldTypeDouble": "double precision", "esriFieldTypeString": "text",
         "esriFieldTypeDate": "timestamptz", "esriFieldTypeDateOnly": "date", "esriFieldTypeTimeOnly": "time",
         "esriFieldTypeTimestampOffset": "timestamptz", "esriFieldTypeGUID": "text", "esriFieldTypeGlobalID": "text",
         "esriFieldTypeXML": "text", "esriFieldTypeOID": "bigint"}

def norm(v, ftype):
    if v is None: return None
    if ftype in ("esriFieldTypeDate", "esriFieldTypeTimestampOffset") and isinstance(v, (int, float)):
        try: return ts(v)                          # epoch ms -> timezone-aware datetime
        except (OverflowError, OSError, ValueError): return None
    return v

Gotchas we hit

  • Field names are lower-cased and sanitized into SQL identifiers; collisions get a trailing underscore.
  • Some date fields hold out-of-range sentinel values that overflow Python's datetime; those become NULL instead of failing the load.
  • A schema signature (md5 of columns, types, geometry type and SRID) is stored so a changed schema triggers a rebuild rather than a broken upsert.

7. Primary keys and OBJECTID stability

What we do

Use the layer's OBJECTID as source_oid bigint PRIMARY KEY. It is the key for paging, upserts, deletes, and the id in every API result.

Why

OBJECTID is present on every layer, unique and indexed by the server, so it is the one key we can always page and diff on.

Alternatives considered

  • GlobalID: more stable across republishing, but not present on every layer (Management Area has one; many permit layers don't).
  • Business keys such as permit numbers: not unique; one permit can have several sequences and polygons.
  • A surrogate serial key: would break every link back to the source.

The code in this repo

CREATE TABLE IF NOT EXISTS sjrwmd.environmental_resource_permit_erp_0 (
  source_oid bigint PRIMARY KEY,         -- the layer's OBJECTID
  objectid bigint, cur_prmt_id integer, prmt_proj_nm text, prmt_stts text, county text,
  recv_dt timestamptz, prmt_decision_dt timestamptz, prmt_expir_dt timestamptz, ...,
  geom geometry(MultiPolygon, 3086),
  _source_url text NOT NULL, _hub_item_id text, _fetched_at timestamptz NOT NULL,
  _source_last_edit timestamptz, _hash text NOT NULL, _geom_repaired boolean NOT NULL DEFAULT false);

Gotchas we hit

  • OBJECTIDs can be reassigned if SJRWMD truncates and reloads a layer. The hash diff then shows up as a mass update/delete, which is correct but noisy; prefer GlobalID for cross-run joins when it exists.
  • ERP OBJECTIDs are large (e.g. 320108305), hence bigint.

8. Provenance columns

What we do

Every row carries _source_url, _hub_item_id, _fetched_at, _source_last_edit and _hash. Every layer attempt is logged in meta.harvest_run, and the latest state per layer lives in meta.layer_registry.

Why

A mirror is only trustworthy if any row can be traced to where and when it came from. The columns travel with the data into the GeoPackage downloads, and the run log answers "when did this layer last change?" without guessing.

Alternatives considered

  • A README note with the download date: lost as soon as rows are copied or joined.
  • Provenance only at the layer level: not enough once incremental updates leave rows of different ages in one table.

The code in this repo

SELECT name, status, server_count, fetched, inserted, updated, deleted, seconds
FROM meta.harvest_run ORDER BY run_id DESC LIMIT 5;
-- a rerun with nothing changed on the server:
-- {"name": "sjrwmd_management_area_viewlayer_0", "status": "skipped", "server": 133, "secs": 1.1}

Gotchas we hit

  • _hash covers the raw attributes and the raw Esri geometry, so it changes only when the source does, not when our parsing code changes.
  • Provenance columns are excluded from the map tiles (they would bloat every tile) but kept in the GeoPackage.

9. Spatial index (GiST)

What we do

Create a GiST index on geom for every table as it is created.

Why

GiST indexes bounding boxes, so ST_DWithin, ST_Intersects and && only examine nearby features. That is what makes the example queries, pg_featureserv and Martin fast. Sizes from our run: land use 2020 has a 14 MB GiST index on a 447 MB table; ERP 4.4 MB on 178 MB; CUP stations 4.0 MB on 80 MB.

Alternatives considered

  • SP-GiST or BRIN: useful for special cases (very large, spatially sorted point tables); GiST is the general-purpose default and fine at this size.
  • No index: every spatial query scans every row.

The code in this repo

CREATE INDEX IF NOT EXISTS environmental_resource_permit_erp_0_gix
  ON sjrwmd.environmental_resource_permit_erp_0 USING gist (geom);

-- uses the index: permits within 1 km of a point
SELECT cur_prmt_id, prmt_proj_nm FROM sjrwmd.erp e
WHERE ST_DWithin(e.geom, ST_Transform(ST_SetSRID(ST_MakePoint(-81.38, 28.54), 4326), 3086), 1000);

Gotchas we hit

  • Queries must compare in the table's SRID (3086). Wrapping the column in ST_Transform(geom, 4326) defeats the index; transform the query point instead.
  • The 4326 views can't use the index for spatial filters, so spatial queries should use the 3086 tables.

10. Incremental updates: lastEditDate skip + hash-diff upsert

What we do

Before downloading, compare the layer's editingInfo.lastEditDate, server count and schema signature with the previous successful run; if all three match, skip it. Otherwise load everything into a temporary staging table with COPY, upsert rows whose hash changed, insert new ones, and delete rows that disappeared, all in one transaction.

Why

Most layers change rarely, so a weekly run should cost a few metadata requests per layer (a skipped layer took 1.1 s). When a layer did change, the hash diff touches only changed rows, and the single transaction means readers never see a half-loaded table.

Alternatives considered

  • extractChanges / change tracking: only 19 services (41 layers) in the inventory have it enabled, so it can't be the general mechanism.
  • Drop and reload every time: simple, but it rewrites every row, churns indexes, and briefly empties the table.
  • Query by last_edited_date: not every layer has editor tracking, and it misses deletes.

The code in this repo

if not force and prev and prev[2] == "ok" and prev[0] == last_edit and prev[1] == server_count and prev[3] == schema_sig:
    return dict(name=name, status="skipped")             # nothing changed on the server

CREATE TEMP TABLE stage (LIKE sjrwmd.<table> INCLUDING DEFAULTS) ON COMMIT DROP;
COPY stage (...) FROM STDIN;                               -- every page streamed in
WITH up AS (
  INSERT INTO sjrwmd.<table> AS t SELECT * FROM stage
  ON CONFLICT (source_oid) DO UPDATE SET <every column> = excluded.<column>
  WHERE t._hash IS DISTINCT FROM excluded._hash          -- only rows that really changed
  RETURNING (xmax = 0) AS ins)
SELECT count(*) FILTER (WHERE ins), count(*) FILTER (WHERE NOT ins) FROM up;
DELETE FROM sjrwmd.<table> t WHERE NOT EXISTS (SELECT 1 FROM stage s WHERE s.source_oid = t.source_oid);

Gotchas we hit

  • lastEditDate doesn't always change when a view layer's underlying data is republished, so the server count is checked as well; --force exists for anything else.
  • (xmax = 0) in RETURNING is the PostgreSQL idiom for telling inserts from updates in one upsert.
  • The weekly GitHub Actions workflow is in the repo but disabled until hosting for the database is chosen.

11. Count reconciliation

What we do

After each load, compare rows fetched with the server's returnCountOnly count; the run is ok only if they're equal, otherwise count_mismatch. qc/qc.sql re-checks table counts against the registry, and the site shows the result per layer.

Why

It is the simplest end-to-end proof that paging didn't drop or duplicate anything. All 15 layers match: 727,495 rows loaded of 727,495 on the server.

Alternatives considered

  • Full geometry and attribute QC reports: useful, but beyond the goal of a faithful copy; validity issues are the source's, and we flag rather than "fix" data.

The code in this repo

Gotchas we hit

  • The count is captured at the start of the run; a layer edited mid-harvest can mismatch legitimately, and the next run fixes it.

12. Exports: GeoPackage, GeoParquet and CSV

What we do

scripts/export.sh writes three files per layer with GDAL and publishes them as GitHub release assets: GeoPackage in EPSG:3086 with provenance columns, GeoParquet (ZSTD) in EPSG:4326, and a zipped CSV with WKT geometry in EPSG:4326, plus SHA256SUMS. 1.9 GB in total; the largest file is the land-use GeoPackage at 519 MB.

Why

Each format serves a different audience. GeoPackage is the open, single-file format QGIS and ArcGIS Pro open natively, with no shapefile limits. GeoParquet is columnar and compressed, the fastest option for DuckDB, GeoPandas and cloud tools. CSV opens anywhere, including Excel. ERP is 214 MB as GeoPackage, 75 MB as GeoParquet and 86 MB as zipped CSV.

Alternatives considered

  • Shapefile: 10-character field names, 2 GB limit, no real date-time, several files per layer.
  • GeoJSON: human-readable but large and slow for 300k polygons; the map uses PMTiles instead.
  • The pg_dump only: useful for PostGIS users, useless for everyone else.

The code in this repo

ogr2ogr -f GPKG    "$OUT/$a.gpkg"    "$PG" "sjrwmd.$t"      -nln "$a"
ogr2ogr -f Parquet "$OUT/$a.parquet" "$PG" "sjrwmd.${t}_4326" -nln "$a" -lco COMPRESSION=ZSTD
ogr2ogr -f CSV     "$TMP/$a.csv"     "$PG" "sjrwmd.${t}_4326" -lco GEOMETRY=AS_WKT
gh release create data-2026-10-28 dist/*

Gotchas we hit

  • GDAL needs its PostgreSQL and Parquet drivers; conda-forge splits them into libgdal-pg and libgdal-arrow-parquet.
  • GitHub release assets are limited to 2 GB each; our largest is 519 MB.

13. PMTiles with tippecanoe

What we do

scripts/build_tiles.sh exports each 4326 view as GeoJSON lines (without the _ provenance columns) and runs tippecanoe into one .pmtiles file per layer: zooms 6–14, at most 500 KB per tile (-M 500000) and 200,000 features per tile (-O 200000). Points are thinned at low zooms (--drop-densest-as-needed), polygons are merged (--coalesce-densest-as-needed --detect-shared-borders) and lines and polygons simplified (--simplification=4).

Why

Small tiles keep the map responsive on phones, and dropping or merging only where tiles are dense keeps the full detail at high zoom. Zoom 6 shows the whole district; at zoom 14 the features are effectively at full resolution.

Alternatives considered

  • A tile server (Martin, pg_tileserv): included in docker compose for local use, but it needs a running server; PMTiles needs only static hosting.
  • One combined PMTiles file: fewer files, but every layer would be rebuilt on any change and the 100 MB file limit would be exceeded.
  • GeoJSON straight into MapLibre: fine for 133 management areas, impossible for 309,325 land-use polygons.

The code in this repo

tippecanoe -q -f -o docs/tiles/$t.pmtiles -l $t -Z6 -z14 \
  --drop-densest-as-needed -r1                               # points
  # --coalesce-densest-as-needed --detect-shared-borders --simplification=4   (polygons)
  --extend-zooms-if-still-dropping -M 500000 -O 200000 $t.geojsonl

# the two heaviest layers, tuned to stay under GitHub's 100 MB file limit:
#  land use 2020: lucode, lccode only; -z12; --simplification=6   159.4 MB -> 44.8 MB
#  ERP: 11 key fields; -z13                                       96.4 MB -> 39.6 MB

Gotchas we hit

  • The first build was 438 MB in total, with land use at 159 MB, over GitHub's 100 MB per-file limit. After tuning: 275 MB in total, largest file 64 MB (streams).
  • --no-tile-stats-attributes-limit isn't a valid tippecanoe option; the first script failed on it.
  • A management-area test build at these settings was 1.3 MB.

14. Serving on GitHub Pages with HTTP range requests

What we do

Commit the .pmtiles files under docs/tiles/ and serve docs/ with GitHub Pages. In the browser, pmtiles.js reads a small header, then fetches only the byte ranges for the tiles in view, and MapLibre draws them.

Why

No server, no tile cache, no cost: Pages answers Range requests with 206 Partial Content and sends Access-Control-Allow-Origin: *, which is all PMTiles needs. Checked on the live site: a 16 KB range of the 64 MB streams file returned 206 with the CORS header.

Alternatives considered

  • GitHub release assets for tiles: we tested this first. Range requests return 206, but there is no Access-Control-Allow-Origin header, so browsers block them. Fine for downloads, not for tiles.
  • Cloudflare R2 or S3: works and scales, but adds an account and a bill; it is the fallback if the tiles outgrow Pages' 1 GB guideline.
  • CARTO raster basemap: its free tiles now show "API key required"; the basemap is Esri's Light/Dark Gray Canvas.

The code in this repo

$ curl -sI -H "Range: bytes=0-16383" -H "Origin: https://example.com" \
    https://knightchrism.github.io/sjrwmd-open-data/tiles/stream_flowpath_24k_hydroedge_11.pmtiles
HTTP/2 206

const protocol = new pmtiles.Protocol();
maplibregl.addProtocol("pmtiles", protocol.tile);
map.addSource(id, { type: "vector", url: "pmtiles://" + new URL(l.tiles, location.href).href });

Gotchas we hit

  • Python's built-in http.server ignores Range, so local previews need a range-capable server (we used npx http-server).
  • Files over 50 MB trigger a GitHub warning on push; over 100 MB are rejected.

15. Reproducing it with docker compose

What we do

Clone, set passwords in .env, start PostGIS with docker compose, and run the harvester. Optional services: pg_featureserv (OGC API Features on :9000) and Martin (vector tiles on :3000).

Why

Pinned images (postgis/postgis:17-3.5) and a single compose file give anyone the same database in minutes, on Linux, macOS or Windows with Docker Desktop.

Alternatives considered

  • Native installs: also documented (EDB installer + Stack Builder on Windows, apt on Linux), but more steps and version drift.
  • A hosted database: the end goal for scheduled updates; not needed to reproduce the data.

The code in this repo

git clone https://github.com/knightchrism/sjrwmd-open-data && cd sjrwmd-open-data
cp .env.example .env               # set your own passwords; .env is never committed
docker compose up -d db            # PostGIS 17-3.5; runs sql/01_init.sql on first start
python -m venv .venv && .venv/bin/pip install -r requirements.txt

Gotchas we hit

  • Port 5432 was already taken on our build machine; PG_HOST_PORT in .env moves PostGIS to another port (we used 55433).
  • On Windows, keep the clone in a local folder such as C:\dev, not OneDrive, which locks and syncs files mid-write.
  • Martin discovers tables at startup; restart it after the first harvest.

Example SQL

All five ran against this mirror on Oct 28, 2026 (3.7 s in total), using the friendly alias views.

-- ERP permits within 1 km of downtown Orlando, nearest first
SELECT cur_prmt_id, prmt_proj_nm, prmt_stts, round(ST_Distance(e.geom, p.g)) AS meters
FROM sjrwmd.erp e, (SELECT ST_Transform(ST_SetSRID(ST_MakePoint(-81.38, 28.54), 4326), 3086) g) p
WHERE ST_DWithin(e.geom, p.g, 1000) ORDER BY meters LIMIT 10;

-- Consumptive-use permit stations inside each district management area
SELECT a.conservation_area, count(*) FROM sjrwmd.management_area a
JOIN sjrwmd.cup_station c ON ST_Intersects(a.geom, c.geom) GROUP BY 1 ORDER BY 2 DESC LIMIT 10;

-- ERP permits decided per county per year since 2020
SELECT county, extract(year FROM prmt_decision_dt)::int AS yr, count(*)
FROM sjrwmd.erp WHERE prmt_decision_dt >= '2020-01-01' GROUP BY 1, 2 ORDER BY 1, 2;

-- Acres of 2020 land use by code inside conservation easements
SELECT l.lucode, round(sum(ST_Area(ST_Intersection(l.geom, e.geom))) / 4046.86) AS acres
FROM sjrwmd.land_use_2020 l JOIN sjrwmd.conservation_easement e ON ST_Intersects(l.geom, e.geom)
GROUP BY 1 ORDER BY acres DESC LIMIT 10;

-- Kilometers of mapped stream flowpath per management area
SELECT a.conservation_area, round(sum(ST_Length(ST_Intersection(s.geom, a.geom))) / 1000) AS km
FROM sjrwmd.management_area a JOIN sjrwmd.stream_flowpath s ON ST_Intersects(s.geom, a.geom)
GROUP BY 1 ORDER BY 2 DESC LIMIT 10;
